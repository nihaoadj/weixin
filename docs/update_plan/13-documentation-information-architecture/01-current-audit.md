# 当前审计

## 已核实事实

| 区域                       | 当前情况                                                                             | 影响                                                   |
| -------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `docs/` 根目录             | 同层放置架构、产品、前端、后端、运行、治理与三份历史记录，共 17 个 Markdown 文件     | 文件名正确但浏览器侧栏缺少分组，首次阅读成本高         |
| `docs/update_plan/` 根目录 | T01–T07 的旧总任务书、七份任务书、执行记录和 `deliveries/` 与 T08–T12 的独立目录并列 | 新旧计划结构不一致，根目录同时承担索引、历史和交付     |
| `docs/README.md`           | 已是文档索引，但只列根目录文件，无法反映实际职责分组                                 | 入口描述与目录形态不一致                               |
| 链接使用者                 | `AGENTS.md`、ADR、T01–T12 文档和交付记录引用现有路径                                 | 移动文件必须更新仓内链接，不能仅依靠目录重定向         |
| Git 工作区                 | 本轮开始前已存在大量 T10–T12 的未提交和未跟踪改动                                    | 只改文档结构和链接，禁止恢复、清理、覆盖或提交既有工作 |

## 当前事实与历史资料的边界

- `architecture.md` 与 `data-layer.md` 是跨模块权威说明，保留在 `docs/` 根目录。
- `api.md`、`database.md`、`backend-module-map.md`、`development.md`、`deployment.md`、`dependency-upgrade.md`、`features.md`、`security.md` 仍承担当前工作参考，不作为冗余内容删除。
- `frontend-editor-motion.md`、`frontend-validation.md` 和 `migration.md` 记录特定阶段的设计或迁移结果，属于可追溯的历史材料，而非每次开发都需阅读的主文档。
- T01–T07 是已完成的早期工程治理计划；T08–T12 已按独立目录组织。所有计划都应采用同一目录结构，差异仅在状态与范围说明。

## 待解决问题

1. 根目录缺少按读者与职责分组的二级入口。
2. 旧计划的任务书和交付证据平铺，未采用与 T08–T12 一致的独立目录结构。
3. 历史材料与当前权威文档并列，容易被误当成当前规则。
4. 路径变更如果遗漏，会造成 `AGENTS.md`、ADR 或交付记录中的链接失效。

## 实施中更新

用户要求 T01–T07 不使用 `archive/` 聚合，而是与 T08–T13 保持同级独立计划目录。本轮据此将每份任务书和任务专属交付证据放入各自目录；只把跨任务的总任务书、执行状态和阶段证据放到同级的 `01-07-engineering-governance/`。
