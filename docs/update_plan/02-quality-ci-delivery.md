# T02 质量门禁、CI 与交付治理任务书

状态：待执行。优先级：P1。执行角色：熟悉 Node/Python 工具链及 CI 的工程师。

## 1. 目标与范围

建立从干净检出到本地检查、CI、合并验收到发布证据的一致流程。现有工具应优先复用，缺少的步骤应补齐；失败返回非零退出码，不用忽略错误或降低门槛换取绿色状态。

负责环境、检查编排、契约生成/漂移、Python 静态检查、截图执行环境和远程合并治理。T01 负责数据库安全，T03/T04 负责架构规则，T05 负责关键用例与覆盖率策略，T06 负责安全规则。不要代替这些任务重新实现同一机制。

## 2. 起点、输入和依赖

必读：[package.json](../../package.json)、[CI](../../.github/workflows/ci.yml)、[Vitest](../../vitest.config.ts)、[Python 配置](../../backend/pyproject.toml)、[依赖规范](../dependency-upgrade.md)、[Playwright](../../playwright.config.ts)、[总计划](README.md)。

已知缺口：check:all 没有契约检查；contract:check 会生成覆盖工作区并用 git diff 判断；Python 未设置格式和类型检查门禁；TypeScript 的 Node 配置只包括 Vite/Vitest，未覆盖 E2E 配置与代码；Windows 截图与 Linux CI 环境不同。

可以立即开展只读环境盘点与脚本设计。运行后端测试必须在 T01 完成后。T03/T04/T05/T06 的命令由其负责方实现，再接入最终流水线，不能因它们未完成而临时永久跳过。

## 3. 分步实施

### T02-01 固定可重复环境

核对 `.nvmrc`、engines、packageManager、CI Node/npm 和 Python 版本，选择一个主验收组合并写清。默认沿用现有 Node 22.13.0、npm 11.9.0、Python 3.12 的意图，先验证兼容再锁定；若需要调整，记录原因并同步所有入口，不默认升级全部依赖。

使用专用虚拟环境、哈希锁定的 Python 依赖和 `npm ci --legacy-peer-deps`。保留 DCloud 同批次升级约束以及当前 peer 兼容说明；不能去掉安装选项后仅凭能安装就认为兼容。

依赖有改动时通过对应工具重新生成锁文件，记录生成环境和来源；严禁手改哈希。仓库配置不硬编码本地解释器路径，Windows/Linux 命令均可执行。补齐全部 `.venv*`、缓存、构建、测试和临时契约目录的 ignore，但不使用过宽规则隐藏源码。

产出：环境矩阵与干净安装记录。完成标准：独立环境可按照说明安装，不依赖全局 pytest/ruff 或残留 node_modules。

### T02-02 修复已知基础检查并扩展静态检查

重新运行只读格式/Lint，限定范围修复已有前端两处格式及后端种子脚本导入排序问题；若基线变化则报告实际差异，不触碰无关用户改动。

接入 `ruff format --check`，将格式化修改与业务改动分开记录。引入并锁定一种 Python 类型检查器，默认采用 mypy：先对配置、公共错误、应用/领域代码建立可执行检查，最终覆盖全部自有应用 Python 文件；第三方无类型库仅允许精确到库的说明，不设全局 ignore_errors。与 T04 配合使重构后的领域/应用层严格检查，允许 ORM 边界分阶段收紧，但要列出剩余规则差异，不得直接跳过整个模块。

扩展 TypeScript 配置，使 Playwright 配置、E2E 和新增工具脚本参与类型检查，避免与客户端 uni 类型不必要混合。编译配置迁移后 `vue-tsc` 仍检查全部页面。

产出：格式/类型命令、锁文件、检查范围表。完成标准：构造一个类型错误或格式错误时对应命令失败，修正后通过。

### T02-03 改造契约检查为只读且可复现

明确三类产物：OpenAPI 快照、生成 TypeScript DTO、合成契约 fixture。为导出器增加统一输出目录或文件参数，在临时目录完整生成、统一格式后与仓库当前文件逐一比较。

`contract:generate` 是显式写入命令；`contract:check` 是只读命令，不覆盖工作树，不以 git diff 对 HEAD 的差异代替内容一致性。这样有意修改且尚未提交的一致快照不会被误判，但 schema 改了而快照未更新仍必须失败。

临时生成不得连接业务库或调用真实服务；处理当前 exporter 导入 app/种子模块的副作用，配合 T01/T04 消除创建业务资源的路径。内容必须确定性；检测缺失、额外或过期产物。T03 移动契约文件时同步输出清单、Prettier、tsconfig、coverage 和 CI 路径。

产出：生成器接口、比较脚本、负向验证。完成标准：连续生成一致；check 前后受检文件 hash 不变；故意改 schema、删除 fixture、手改 DTO 均失败；显式重新生成后通过。

### T02-04 统一检查命令和失败行为

按总计划的命令合同接入安全测试、格式、Lint、前后端类型、架构边界、完整和关键覆盖率、契约、双端构建、依赖审计、秘密扫描、API/Demo E2E。

`check` 保持前端快速完整检查；`backend:check` 管理后端静态和测试；`check:all` 包含所有必需项，可避免重复运行已涵盖的子检查，但不能把关键覆盖率检查换成普通测试。

工具脚本应使用跨平台进程调用与退出码传递，避免 shell 特定的环境赋值、目录切换和路径拼接。失败可尽早停止，但最终报告必须列出哪些步骤未执行。不得使用 continue-on-error、命令末尾强制成功、无条件空报告来掩盖失败。

产出：命令职责表及脚本集成。完成标准：本地与 CI 每项规则一致，名字和覆盖范围可核对。

### T02-05 固定 E2E 与截图环境

默认以锁定 Linux/浏览器环境作为共享视觉基线源；Windows 开发者通过等价容器、WSL 或 CI 预览生成基线。记录 OS 镜像、浏览器、字体、viewport、时区、语言、DPR、固定数据/时钟、动画处理方式。

先核实当前 win32 图片在 CI 的实际寻址和缺失行为；在目标环境生成对应基线并人工审阅差异。不能仅把文件后缀改成 linux，不能为了通过调高像素容差，不能在正常验收流水线运行 --update-snapshots。

如保留双平台基线，必须明确维护责任并实际验证两套，不把 Windows 与 Linux 渲染等价作为假设。API 与 Demo 的报告分别保存，避免后一次覆盖前一次。CI 除失败截图外还保留 trace、测试摘要，制品不含敏感数据。

产出：平台基线策略、审阅记录、两次无自动更新的稳定回归。

### T02-06 接入 CI 与依赖安全

保留契约/前端/后端任务的独立反馈，最终 E2E 在前置成功后运行；接入 T06 的秘密扫描及既有生产/全量 npm 审计和 Python 审计。保持 npm high/critical 零容忍及无 advisory 白名单规则；Python 已知漏洞按既有更严格策略处理，不能偷偷降级。

CI 权限最小化，第三方 action 固定可审查的版本或提交，缓存键含锁文件，不把 .env、数据库、认证缓存上传。PR 不执行可窃取生产 secrets 的不可信代码，不为使测试通过下发真实业务凭据。

增加稳定名称的汇总检查 `Engineering gate`（目标名称），只在所有必需任务成功时成功。取消、超时、依赖失败、意外 skip 都不能被汇总为成功。验证工作流触发分支覆盖实际开发与 PR 流程。

### T02-07 配置远程合并约束并交付

先只读确认 GitHub/Gitee 哪个是实际主协作库，以及默认/发布分支。项目同时配置两个 remote，不假定 GitHub Actions 会保护 Gitee 合并。

准备具体规则：必需 Engineering gate、禁止普通直接推送、至少一位独立审阅者（团队具备条件时）、过期审批处理、绕过权限清单；若使用合并队列，保证相应事件也能得到检查。对安全敏感模块配置合适的审阅责任。

仓库外设置需要相应账号权限与明确授权。先提供可审阅的规则变更，再由已获授权执行者或管理员应用；没有权限则交付配置清单和阻塞项，不能声称已启用。用一个故意失败的临时 PR 验证无法合并，再验证恢复后的结果；不得通过关闭保护制造演示。

## 4. 验收矩阵

| ID    | 检查方式                                          | 通过条件                                         |
| ----- | ------------------------------------------------- | ------------------------------------------------ |
| CI-01 | 干净检出，按文档安装及执行                        | 环境版本可追溯；无全局依赖                       |
| CI-02 | format、Lint、TS、Python 类型各注入一次错误       | 对应步骤返回非零，错误位置明确                   |
| CI-03 | 改 schema 不生成；手改/删除产物；一致的未提交产物 | 前两类失败，后一类按实际内容通过；检查不写文件   |
| CI-04 | 前后端分别注入一条禁止导入                        | 架构检查及最终门禁失败                           |
| CI-05 | 关键模块漏覆盖或低于阈值                          | T05 的门槛实际使 CI 失败                         |
| CI-06 | Linux 视觉回归连续运行两次                        | 不更新基线即可通过；差异人工审阅                 |
| CI-07 | 使用合成秘密样本验证扫描器                        | 检出并失败，日志不暴露完整样本                   |
| CI-08 | 一个必需任务失败/取消/意外跳过                    | 汇总不能成功；远程策略启用后不能合并             |
| CI-09 | 正常变更完整运行                                  | check:all 和同一提交 CI 通过，制品完整           |
| CI-10 | 两个 remote 的策略核对                            | 实际主仓库受到保护，其他 remote 的风险和职责明确 |

故障注入在临时副本、测试 fixture 或专用分支进行；不得污染真实业务库或把故意失败代码混入最终交付。

## 6. 回退与外部阻塞

对工具升级问题回退该批工具及锁文件，保留已有安全和测试门禁；不能通过关掉失败检查回退质量标准。图片基线回退到对应平台的已审阅版本，不用自动接受覆盖。远程保护变更需保存原规则和恢复步骤，由有权限的执行者操作。CI 网络、账号、额度、Linux/容器能力不足时记录可复现错误和解除条件，不以本地部分通过代替完整完成。
