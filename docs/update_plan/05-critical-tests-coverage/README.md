# T05 关键业务回归与覆盖率治理任务书

状态：阶段任务书。原始计划状态为“待执行”；实际仓库侧证据见 [T05 最终交付记录](deliveries/T05-final.md)。优先级：P1。执行角色：能阅读前后端业务代码的测试开发工程师。

## 1. 目标与边界

把“现有测试能跑”和“关键业务得到保护”区分开：建立按风险组织的用例矩阵，补足失败/越权/并发路径，并以独立覆盖率门槛持续约束关键模块。

本任务负责业务测试、coverage、E2E 场景、性能及端侧验收；不另建数据库启动方案，不代替 T02 管理截图平台，不把生产密钥/真实微信调用加入普通 CI。测试应验证可观察行为，而不是逐行复制实现或只检查 mock 被调用。

## 2. 输入与阶段依赖

必读：[数据层规范](../../data-layer.md)、[功能](../../product/features.md)、[安全](../../governance/security.md)、[Vitest](../../../vitest.config.ts)、[Python 配置](../../../backend/pyproject.toml)、[现有 E2E](../../../e2e/pilot-flow.spec.ts)、[总计划](../01-07-engineering-governance/README.md)。

重要起点：[remoteAuth.spec.ts](../../src/services/remoteAuth.spec.ts)仅覆盖一个 Demo 登录成功场景；[medical_ai 测试](../../backend/tests/test_medical_ai.py)只有部分模型调用路径；[缓存测试](../../src/services/apiClient.cache.spec.ts)、[访问控制测试](../../backend/tests/test_access_control.py)、[数据层测试](../../backend/tests/test_data_layer.py)已有断言，应复用扩展。

T05-01 可立即只读开始；运行后端测试依赖 T01。T05-02 是 T03/T04 重构的前置交付，之后持续跟随模块迁移补测；本任务最终验收在 T03/T04 完成后进行。不要求重构等待本任务全部结束。

## 3. 测试分层策略

| 测试层       | 验证什么                                            | 环境及禁止事项                                            |
| ------------ | --------------------------------------------------- | --------------------------------------------------------- |
| 领域单元     | 评分、状态转换、规则边界                            | 纯输入输出；不启动框架或数据库                            |
| 应用用例     | 编排、失败、权限、事务意图                          | 注入 fake port；断言结果与持久化状态，不只看调用次数      |
| adapter/合同 | API DTO、Zod、SQL 查询、存储迁移、API/Demo 合同行为 | 受控 HTTP mock 或临时 DB；不访问真实 AI/微信              |
| API 集成     | 认证、响应字段、事务回滚、资源可见性                | T01 app/client/db fixture，包含真实 SQL 但仅临时库        |
| H5 E2E       | 完整用户旅程和页面反馈                              | 固定合成数据；T02 指定浏览器/截图环境                     |
| 微信端验收   | 条件编译、平台登录、路由、网络域名、真机行为        | 开发工具/测试账号；单独记录设备与配置，不冒充 H5 自动覆盖 |

单个模块的测试应跟随其职责迁移；跨模块合同、API 和 E2E 独立保留。领域测试不应依赖 UI 文案，视觉测试不应承担全部业务正确性。

## 4. 分步实施

### T05-01 建立需求—风险—用例矩阵

从本任务第 5 节与实际路由/用例盘点，给每个场景分配 ID、负责模块、前置数据、动作、成功/失败断言、测试层、现有用例和缺口。区分已存在的安全行为与待 T06 确认的政策，不让旧漏洞被固化成“正确行为”。

记录基线环境与所有测试/coverage 文件清单。本会话的 79/47 个测试及旧覆盖率仅作起点，不能用测试数量替代质量。

### T05-02 建立重构前行为基线并交接

T01 完成后运行现有全套测试，优先补报告提交/批阅、登录角色不匹配、API 不降级 Demo、数据隔离和训练幂等的特征测试。保存响应字段、状态变化、数据数量等稳定基线，不用整个动态时间戳响应快照制造噪声。

对现有失败标明“已有问题/新发现安全缺陷/测试环境问题”；由实现负责人修复或确认期望。向 T03/T04 交付可执行的样板链路回归和已知缺口，不能只交自然语言说明。

### T05-03 补齐认证、会话、合同与存储测试

按第 5 节 AUTH、DATA 矩阵扩展测试。使用 deferred Promise 控制乱序请求，fake clock 验证 TTL，不用随意 sleep。覆盖登录失败仍保留旧会话、成功后统一更新身份、角色失败不保存新 token 的完整可观察状态。

微信 `#ifdef` 条件编译不能按普通 TypeScript 执行结果代替双平台语义；通过平台 adapter 测试和实际两端构建/冒烟区分微信与 H5。

### T05-04 补齐报告、发布、训练、AI 与统计测试

按第 5 节业务矩阵实施；优先写能在引入真实缺陷时失败的测试。数据库异常应验证回滚后的记录而不只检查错误码；并发使用屏障/独立会话启动，不能拿顺序调用冒充竞争测试。

AI 外部响应构造超时、503、无效 JSON、空 choices、错误类型、空内容和隐藏字段注入样例；断言有界重试、fallback、日志脱敏与确定性评分。预期医学文案由已有规范/T06 核定，不自行编造新的临床政策。

### T05-05 建立完整覆盖率范围与关键门槛

更新 include/glob，使所有手写前端业务代码，包括迁入 features 的用例、平台客户端、composable 和 Vue script，被实际统计；配置必要的 Vue 测试编译与 source map，并验证未导入实现仍出现在报表。类型声明、生成 DTO 和纯资产可排除，排除项需要理由，不允许整包业务豁免。

后端 app 自有实现进入统计；ORM 声明型映射可沿用精确排除，但任何混入其中的业务方法必须纳入。迁移和脚本用独立行为测试保障，不把排除覆盖率等同于无需测试。

新增 `test:critical`、`backend:test:critical`，以真实职责映射关键文件，既运行用例又检查覆盖率。关键组为空、路径失配、文件未入报表必须失败。后端若采用覆盖率 JSON 解析脚本，应测试边界值、缺失文件、零分支文件和不合格结果，不能默认为通过。

### T05-06 完成 E2E、性能和微信验收

保留并扩展已有 pilot、structured-case、review-and-class、data-layer、empty-states、demo-flow。按角色流程安排独立数据，覆盖刷新/重进、无数据、失败重试和重复点击，不只走成功页面。

截图由 T02 固定环境和审阅，普通 CI 不自动更新。每个核心行为断言应独立于截图，即使截图容差改变也不能掩盖权限或数据错误。

性能测试保留固定数据规模、SQL 计数和分页断言。微信开发工具/真机使用合成账号与病例，明确真实登录/域名配置是否具备；缺少设备或账号应作为外部待验收，不能写“已通过”。

### T05-07 证明测试有效并交付

在临时副本对关键守卫做一次受控故障注入，例如去掉 owner 过滤、关闭旧会话保护、移除审核 digest 比较、重复生成计划。每类均应有对应测试失败，随后恢复并复验；无需为了此目标引入完整 mutation framework。

汇总原路径与新职责覆盖率、用例矩阵及缺口，交 T02 接入最终 CI、交 T07 更新验收命令。不能通过删除失败断言或降低原门槛完成。

## 6. 目标覆盖率与范围防退化

以下是本轮交付目标，不是当前已达到的事实：

| 范围                                                             | 行/语句            | 分支                   | 函数               |
| ---------------------------------------------------------------- | ------------------ | ---------------------- | ------------------ |
| 前端全部手写业务实现                                             | 至少 85%           | 至少 80%               | 至少 85%           |
| 前端关键职责：登录/会话、HTTP 缓存、存储迁移、报告/训练用例      | 每个职责组至少 90% | 每个职责组至少 85%     | 每个职责组至少 90% |
| 后端全部手写应用实现                                             | 至少 85%           | 启用分支统计后至少 80% | 不单独设置         |
| 后端关键职责：认证授权、医学 AI 安全、发布/审核、评分/计划状态机 | 每个职责组至少 90% | 每个职责组至少 85%     | 不单独设置         |

职责组应在机器可读清单中映射到明确实现文件，禁止合并大量种子常量拉高平均数。重构后原 remoteAuth、medical_ai、personalized 等代码迁入新文件仍继承其职责门槛。零分支/零函数文件按适用指标检查，不能把缺少报表误认成零分支。

覆盖率达到数字也不替代第 5 节的安全/业务行为。对于新增目标因现有缺口未达到，应继续补测或报告阻塞，不能擅自降低要求。

## 9. 回退与维护

测试重构不改变业务预期；先定位 flaky 来源再修改等待条件、数据或生命周期，禁止用 retry 无上限和超长 sleep 掩盖竞态。工具版本造成 coverage/source map 回归时回退工具批次，不删除关键职责检查。长期维护由模块执行者补对应测试，T05/T02 的清单与门禁保持强制执行。
