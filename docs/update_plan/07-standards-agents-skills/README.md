# T07 工程规范、AGENTS 与项目 Skill 任务书

状态：阶段任务书。原始计划状态为“待执行”；实际仓库侧证据见 [T07 最终交付记录](deliveries/T07-final.md)。优先级：P1。执行角色：能理解项目架构与自动检查的工程负责人/文档维护者。

## 1. 目标与范围

建立一套人和 AI 都能执行的项目规范：正式文档描述真实架构和流程，AGENTS.md 提供持续项目约束，项目 skill 提供按改动类型执行的工作流，CI 负责可自动化的强制检查。

本任务不是复制多份同样规范，也不是仅安装几个通用 skills。必须解决现有说明冲突，并让执行者在新环境中能够按文档完成一次真实的开发和验收。

只创建与本项目有关的本地指导。不要修改用户全局 Codex 配置、全局权限或其他项目；不要把当前任务的授权扩大为自动部署、推送、密钥轮换等权限。

## 4. 分步实施

### T07-01 建立规范基线与完成定义

先写入或整理简短的项目级规则：不覆盖未提交工作；API 失败不能切 Demo；客户端禁止服务端秘密；权限在后端校验；测试只用受管数据库；生成文件不手改；接口变更同步合同；数据库变更有迁移/恢复说明。

与 T03/T04 确定八个业务模块、层名称、公开接口和跨域编排术语。目标架构标为“计划”，现状标为“当前”，避免重构前就发布与实现不符的强制路径。

产出：规范基线、文档责任表、通用 Definition of Done。完成标准：各执行者知道要引用哪些文档、哪些要求必须保留、哪些路径尚待实现。

### T07-02 修复现有文档冲突并随模块更新

更新 development 中 Demo 数据写在 repository.ts 等旧说明，使其与当前数据层及后续模块迁移一致。统一 npm 安装、Python 虚拟环境、运行目录和安全测试命令，不再展示会误用开发库的无保护示例。

更新实际迁移 head 和字段说明：编制时已有 0008 与工作区 0009，不能继续只写 0007；以执行时 Alembic 图为准。移除数据库只改 URL 即可安全迁移的无验证承诺，给出尚需完成的兼容测试。

更新架构图中的实际依赖方向，不能把 SQLite→PostgreSQL/AI 的概念路线画成真实调用链。将 ApiRequest、storage、平台登录、模块用例和装配入口映射到新结构，清理失效链接与旧路径。

所有领域任务交付时提交文档事实变更，T07 负责整合，而不是让领域执行者等待文档维护者才修正错误说明。

### T07-03 建立 AGENTS.md

根目录 AGENTS.md 至少包括：技术栈与边界、必读文档、安装与检查入口、按任务范围选择验证的规则、禁止行为、已有变更保护、生成契约/迁移政策、交付证据格式。

只有存在确实不同的局部要求时才新增 src/backend 下的 AGENTS.md；不为每个小目录复制一份。确保局部规则不与根规则冲突，不指示跳过更高优先级安全或用户要求。

代码审查规则聚焦可观察风险：越权、数据泄露、事务和幂等性、运行模式混写、生成合同漂移、架构反向依赖。格式和机械规则由 CI 自动处理，不用长篇提示替代工具。

每个命令需说明当前可用状态与适用范围；不能写“任何任务都跑生产迁移”或“为让测试通过自动关闭权限”。外部操作按现有授权边界执行，不为普通可逆代码修改增加无必要确认。

### T07-04 创建项目级工程 Skill

使用当前可用的 `skill-creator`，执行时先读取其指导；目标 skill 名为 `wx-engineering-standards`，创建在仓库 `.agents/skills/wx-engineering-standards/`，提交到版本控制供团队复用，不安装到个人全局目录代替项目交付。

SKILL.md 包含有效 name/description，触发范围明确：本项目功能修改、修复、重构和代码审查；纯文案或无代码分析不自动触发重型全套验证。所有安全限制、目录和命令引用正式文档，不在 skill 内复制易失效的实现清单。

工作流必须覆盖：

1. 查看 git 状态和适用 AGENTS，识别本次范围及已有工作。
2. 根据模块/改动类型读取必要的权威文档，不一次读完整文档库。
3. 确认用例、业务规则、IO、DTO/模型所属层及受影响公开接口。
4. 修改实现，并判断是否同步合同、迁移、运行模式、权限和测试。
5. 按第 5 节验证矩阵执行可用命令，保留退出码、覆盖率范围和未执行原因。
6. 自检架构边界、安全和兼容性，交付变更、证据、风险、回退信息。

skill 可以附带命令路由脚本或检查表，但必须复用 package scripts，不另写第二套测试/coverage 逻辑。失败不能吞掉，不得自动安装外部插件、索要生产凭据或扩大权限。

### T07-05 整理可选官方 Skill 参考

核对实际可安装目录及源内容，仅推荐适合本项目的用途：security-best-practices（Vue/TS/FastAPI 安全）、security-threat-model（信任边界）、gh-fix-ci（GitHub 检查故障）、playwright（H5 浏览器辅助）。它们不是当前已安装的前提，也不是本轮完成的必需依赖。

如用户另行要求安装，再按安装技能流程实施；不为了编写规范一次性安装全部。第三方指引不能覆盖项目实际合同；安全/浏览器 skills 的结论不能替代 CI、真机或医学验收。

产出：用途、来源、触发条件和限制说明，保持简洁，不建设泛化 skills 商城。

### T07-06 建立贡献和交付工作流

在 development 或引用的贡献说明中规定：按领域/模块组织提交、结构重构与行为改变分开说明、涉及安全和数据库需要相应审阅、生成文件与源码一起更新、提交前检查、CI 失败归属、回退信息。

提供 PR/交付模板，包含为什么改、改了什么、合同/数据影响、测试与未验证项、架构/安全检查、回退步骤；可以采用团队已有 commit 风格，不为形式引入与目标无关的繁重流程。

定义责任角色而非虚构人员：模块维护者、集成负责人、仓库管理员、凭据管理员、医学内容审核者。跟踪外部事项不泄露敏感信息，不把“需要管理员”写成执行者可以假定完成。

### T07-07 验证文档和 Skill 可实际执行

在干净副本/临时分支中按文档安装、运行示例命令；对新任务验证 AGENTS/skill 可被实际发现，不能仅因文件存在就宣布启用。

使用第 6 节代表性样例做 dry run 或小型可逆修改，检查 skill 是否选择正确文档和命令、是否识别未提交改动、是否明确未验证项。不要为了展示 skill 而修改生产数据或真实配置。

校验 Markdown、本地链接、文件路径、命令存在性、术语和实施状态。最终与 T01～T06 的交付命令表对照，不留未来脚本被描述为已经可用的情况。

## 5. 改动类型与最小验证路线

以下矩阵应在交付时使用已落地命令；最小路线用于开发反馈，合并仍需 T02 完整门禁。

| 改动类型           | 开发期间至少验证                                                        |
| ------------------ | ----------------------------------------------------------------------- |
| 纯 Markdown        | 限定范围 Prettier、链接、命令/路径正确性；不无谓运行数据库              |
| 前端 UI/页面       | 格式、Lint、类型、相关组件/用例测试；涉及跨端 API 时双端构建            |
| 前端业务/存储/身份 | 上述 + frontend:boundaries、完整/关键 coverage、对应 API/Demo 行为      |
| 后端领域/用例      | 安全测试环境、Ruff/类型/边界、单元与 API 集成、关键 coverage            |
| API/schema/mapper  | 双方类型检查、contract:generate 后 contract:check、合同与端到端消费测试 |
| 数据模型/迁移      | 安全 fixture、空库/旧库/head 迁移、数据保留/回退范围、完整后端回归      |
| 权限/AI/敏感数据   | 对应安全矩阵、关键测试、秘密/日志验证；必要时 T06 复审                  |
| 依赖/构建/CI       | 锁定安装、双端构建、审计、完整检查、CI 负向验证                         |
| 跨模块结构调整     | 依赖图/边界自测、路径/生成/coverage 同步、完整回归和文档                |

API 合同纯格式变化也要确认生成确定性；纯文档更新不需要创建镜像实现测试。任何跳过都给出原因，不能写“无需验证”笼统结束。

## 8. 回退与后续维护

指引造成错误触发时可在仓库回退对应修改，保留正式工程安全要求；不修改用户全局设置来隐藏问题。重大目录/命令/合同变化必须同步文档与 skill 引用；模块维护者负责事实，集成负责人负责一致性。后续只保留少量权威文档和必要 ADR，避免为每个小修改新增一份重复规范。
