# 前端体验设计：临床带教记录单

更新：2026-08-31。本文件描述当前实现及本轮设计决策；验证结果见 [前端验收记录](../records/frontend/validation-2026-08-31.md)，工程边界仍以 [架构](../architecture.md) 和 [数据层](../data-layer.md) 为准。

## 1. 设计方向与问题诊断

界面服务于医学教学，不模拟临床诊疗系统。核心阅读顺序是「学习任务 → 推理证据 → 教师反馈」。

本轮反馈指出两个具体问题：

- 教师页面先摆大待办卡，再在页面中间切换报告/问题，导致导航与内容一起滚走，进入某项任务前必须反复略过不相关信息。
- 报告批阅把元信息、对话、AI 分析、问题建议和表单层层包在圆角框里；几乎每段内容权重相同，AI 分数反而成为主角。

解决方向是用明确的任务分区与文档排版建立层级：导航属于应用壳，原文属于阅读区，AI 输出属于参考层，教师评价属于编辑区。圆角、颜色和边线只表达这些区别，不承担装饰密度。

另一个独立问题是运行同步：微信工具导入的 dev 目录与生产构建目录不同，且 Zod 默认动态编译在微信沙箱中报错。目录和启动修复不等于设计已通过；H5 与微信必须分别验收。

## 2. 当前实现范围

| 范围               | 当前实现                                                              |
| ------------------ | --------------------------------------------------------------------- |
| 登录与学生学习主页 | 身份入口、首次学习引导、下一项行动、学习证据与统一导航                |
| 学生问答           | 左对齐建议问题、连续消息、可见输入标签、报告与重试入口、底部输入区    |
| 教师主工作区       | 工作台 / 报告 / 问题三个独立视图，手机底部导航、桌面左侧导航          |
| 教师内容列表       | 创建操作集中在顶部，状态筛选吸顶；空态不重复创建按钮                  |
| 报告批阅           | 无嵌套卡片的记录单、完整原文、分级参考意见、人工评价编辑区            |
| 跨端基础           | 设计令牌、焦点、键盘激活、H5 原生输入可访问名称、安全区与微信启动兼容 |

没有重做所有病例训练、学生报告、班级/分析/医学审核详情页。本轮不新增生产业务 API、权限、DTO 字段或数据库迁移；也不虚构班级归属、批阅教师姓名、自动保存或通知能力。

## 3. 视觉系统

### 3.1 色彩与边界

| 令牌           | 当前色值              | 用途                             |
| -------------- | --------------------- | -------------------------------- |
| Paper          | `#F6F8F6`             | 工作区底色、教师编辑分区         |
| Surface        | `#FBFDFD`             | 阅读表面                         |
| Ink            | `#102A43`             | 主标题、正文重点                 |
| Clinical       | `#0A6B66`             | 主操作、当前导航、人工评价定位线 |
| Safety         | `#9A5618`             | 需核对内容与教学安全提示         |
| Alert          | `#B8454F`             | 错误、拒绝等状态                 |
| Muted / Border | `#5E7382` / `#D4E0DC` | 辅助信息 / 结构分隔              |

使用 `App.vue` 中的语义令牌，不为每个面板另造一套颜色。状态必须配文字，不能只看颜色。

### 3.2 字体层级

统一使用系统中文无衬线字体：PingFang SC、HarmonyOS Sans SC、Microsoft YaHei 等。早期“标题宋体 + 正文无衬线”的方案已撤回，避免跨端字体落差。序号和少量数值采用 utility 等宽栈。

批阅记录单的手机层级为：

1. 文档主标题：48rpx、800 字重，识别报告归属。
2. 分区标题：36rpx、700 字重，定位原文 / 参考 / 教师评价。
3. 原文：30rpx、1.8 行高；学生原文较深，AI 对话稍弱，同时保留角色文字。
4. 辅助说明、状态与时间：22–24rpx；320px 窄屏设置 12px 下限。
5. 桌面主标题 36px、分区标题 20px、原文 16px、说明 13–15px。

时间、序号、状态不与正文抢重量。英文只用于 AI 等必要术语，不使用无意义的英文眉题。

### 3.3 空间与表面

- 普通列表仍可使用一层细边框容器；内部正文不再套气泡。
- 批阅正文使用无圆角、无阴影的连续纸面。标题下用细墨线建立文档起点，对话条目间用浅分隔线。
- AI 待补充建议用窄琥珀批注线，不使用整块黄色提示卡。
- 教师表单为一整块浅底编辑区，顶部青色细线，控件圆角仅 4px。这里的底色表达“可编辑”，不是给每段内容加框。
- 交互热区至少 44px；主要提交按钮至少 48px。不能只用 rpx 推算窄屏热区。
- 间距以 4/8/12/16/24/32px 及相应 rpx 级差组织，分区距离大于段落距离。

## 4. 教师主工作区

### 4.1 导航与滚动

教师默认进入 PBL 工作区，先看到活动课堂、诊断待办和学习结果核验。概览、报告、问题和 PBL 各自只承载对应任务；四个视图不叠在同一页。

手机结构：

```text
┌─────────────────────────────┐
│ 教学查房 / 当前工作区    退出 │ 固定页眉
├─────────────────────────────┤
│ 新建问题        生成病例      │ 问题区的吸顶工具栏
│ 待审核                已发布 │
├─────────────────────────────┤
│                             │
│ 当前工作区列表               │ 仅这里纵向滚动
│                             │
├─────────────────────────────┤
│ 工作台       报告       问题 │ 固定主导航 + 安全区
└─────────────────────────────┘
```

桌面 ≥900px 将主导航放到 176px 左侧栏，内容最大宽度 840px；整个应用壳最大 1080px。不能通过一排放大的手机按钮来充当桌面导航。

### 4.2 状态与返回

- 深链接支持 `?tab=overview|reports|problems|pbl`；首次访问时挂载，后续在同页保留已打开工作区并刷新其数据，不累积页面栈。
- 打开详情使用正常下钻；保存或返回时恢复原工作区。
- 工作台计数加载失败显示“重试”和错误说明，未知计数不能显示为 0。
- 医学审核入口只在现有会话具备 `medical_review` 权限时显示；真实授权仍由后端执行。
- 内容区只有顶部一组“新建问题 / 生成病例”。空态解释下一步，不再重复这两个按钮。
- “恢复示例内容”是 Demo 辅助操作，放在列表底部，保留原有确认，不与创建操作并列。
- “待审核 / 已发布”是列表筛选，使用具备 `aria-pressed` 的按钮组，不伪装成未实现键盘模式的 ARIA tab。

## 5. 报告批阅：四层阅读层级

### 5.1 页眉：报告归属

以“学生的推理记录”为主标题，显示真实学生名称、提交时间、待批阅/已批阅状态。AI 分数不放进页眉，也不放大为成绩英雄区。

### 5.2 原文：批阅的依据

- 按原始顺序展示完整对话，不折叠、不截断。
- 每条记录用序号、学生/AI 角色和已有时间戳定位，不再使用头像方块或聊天气泡。
- 保留换行，并允许长中文与长英文字符串换行。
- 阅读区没有输入框、营销提示或重复操作，保持连续扫读。
- 原文为空有中性说明，不把空记录描述为“表现良好”。

### 5.3 AI：辅助判断

“AI 参考意见”包含摘要、已有表现、待核对与补充、后续学习建议。仅渲染实际存在的列表，避免之前只展示第一条优势、遗漏后续建议。

参考评分以普通元信息呈现，并明确“仅供教学参考，最终评价由教师给出”。没有 AI 问题项不等于内容正确，仍提示教师核对。医学内容原文不由本次视觉改版改写。

### 5.4 教师：最终编辑区

手机放在原文与参考意见之后，以整段浅底和青色顶线定位。桌面 ≥1000px 放在右侧 304px 列，随阅读保持可用；这样能一边核对原文一边写反馈。

```text
┌─────────────────────────────────────────┐
│ 学生学习报告                     待批阅 │
│ 示例学生的推理记录                      │
│ 提交于 2026-08-28 18:00                  │
├─────────────────────────┬───────────────┤
│ 01 对话原文             │ 03 教师评价   │
│ 01 学生        时间     │ 评分 0–100    │
│    完整原文……           │ [        ]    │
│ ─────────────────────── │               │
│ 02 AI 教学助手   时间   │ 给学生的反馈  │
│    完整回复……           │ [           ] │
│                         │ [           ] │
│ 02 AI 参考意见          │               │
│ 参考评分 · 摘要 · 建议   │               │
├─────────────────────────┴───────────────┤
│ 尚未提交 / 提交后学生可查看   [提交批阅] │
└─────────────────────────────────────────┘
```

表单和提交规则保持兼容：

- 评分范围 0–100；反馈选填，仍为原 UI 的 1000 字上限，不借设计改动扩大合同。
- 评分错误出现在字段下，并聚焦字段；保存错误出现在提交区，保留输入，允许明确重试。
- 保存中禁用表单与提交按钮，阻止重复请求。只有服务返回成功才提示保存并返回。
- 已批阅报告回填原评分/反馈，允许继续修改，按钮改为“更新批阅”。
- 底部提交栏限制在应用壳内，预留 140px 加安全区，最后一段表单不能被遮住。
- 本页没有自动保存；不能用“已自动保存”或不存在的通知承诺误导用户。

## 6. 学生端的同一语言

登录：手机先介绍学习闭环再选择身份，桌面说明与身份面板分列。

学习主页：首次使用提供可执行引导；有记录后突出下一项行动，能力信息作为证据，不堆叠仪表盘。

问答：去掉居中英雄卡、英文眉题和渐变。建议问题为左对齐行按钮；输入区明确标为“你的问题”，发送、重试、生成报告具有独立语义。页面用弹性布局留出消息滚动区，不把固定输入框叠在内容上。

## 7. 跨端与可访问性实现

- 手机布局使用 rpx，并补窄屏文字和触达下限；600px 起将主要文字、内边距切换为稳定 px，防止平板上控件膨胀。
- 工作区手机固定底部主导航，900px 起换侧栏；批阅详情1000px起才分栏，以保证表单与原文宽度。
- 小程序视口用 `100vh`；H5 的 `100dvh` 只在 H5 条件编译内。已发现把同一声明发给小程序会使底部导航回到内容中部。
- 自定义 `uni-button` 在 H5 补 Enter/Space 激活。原生 HTML button 保留自身默认行为，不重复合成点击。
- 当前 uni-app H5 把输入 ARIA 属性放在外层 wrapper。仅 H5 启用 `nativeFieldA11y`，将名称与错误关联同步到实际获得焦点的 input/textarea；不复制输入值、不访问业务数据。
- 使用可见标签、标题层级、命名导航、当前项状态、焦点环与减少动效规则。装饰图标提供空 alt，不重复朗读。
- 这些实现不等于已完成所有设备的读屏认证。真机键盘、安全区和读屏仍需独立验收。

## 8. 审阅决定与剩余目标

主工程师负责信息架构、设计方案、落地审阅与最终多端检查；Terra High 子代理完成了视觉/边界复核，重点确认已批阅修改、权限范围、字段真实性和固定栏遮挡。另一项无障碍子审阅仅收到部分结果，不能视为完整审计。

保留的后续目标：

- 病例五阶段页、学生报告和教师分析详情的文档化改版。
- iOS/Android 微信真机软键盘与读屏复验。
- 在完整教学数据与真实教师使用中验证密度、长列表和反馈效率。

本轮不以更新截图基线代替审阅。每张新基线须先确认变化符合本设计；错误状态、API/Demo 隔离、返回路径和提交语义仍要单独测试。
