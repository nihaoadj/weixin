## 报告修复

受控命令 `backend/scripts/rebuild_t43_reports.py` 默认 dry-run，显式 `--database` 指向已确认、本人受管的非生产 SQLite。仅对已冻结包、完整终态评价且报告缺失的记录重建确定性 payload；已有同摘要和同内容报告跳过，异摘要或身份冲突停止并回滚本次写入，不覆盖历史。缺失终态证据计为 `incomplete_evidence`，不虚构报告。通过 learning 应用用例和同一 report builder 执行，不在 GET 写入。

`--apply` 同时要求 `--confirm-development` 及新的 `--backup` 路径；命令先用 SQLite backup API 备份并做完整性检查，再在一个事务内重建。受管测试已覆盖干跑、备份、成功恢复、缺证据跳过和摘要冲突；真实开发库的恢复演练仍待执行，不能以本地 fixture 代替。命令拒绝 production 环境，不增加公开教师“重新生成”按钮，不对生产自动重放。

目标绑定修正改变内容审核摘要输入，但不增加 schema。现有 `medical_reviews.case_digest` 历史记录不删除、不迁移、不批量改写；当前服务端在旧摘要不匹配时按审核已失效处理。受管部署前须评估旧病例资源不可用影响，并安排逐内容复审；如正式审核资源暂不可用，应显示阻塞并暂停使用该资源，不得用 migration、seed 或后台脚本把旧批准印章成新摘要。回退代码不能让旧摘要假装覆盖新关联：若必须恢复旧算法，需另行批准安全回退、停止新课堂评分资源发布并确认目标关联仍能被独立可信地验证。

正常新流程报告与终态同事务，不应出现缺报告；修复工具仅服务历史恢复/受控异常。缺证据必须保持待处理，不能AI补造分数。日志仅计数和内部关联，不输出学生内容。
