# ADR-0001：保留原生微信小程序并渐进式使用 CloudBase

- 状态：已提议
- 日期：2026-08-07
- 决策者：项目负责人、技术负责人、产品负责人（待确认）

## 背景

仓库已经使用原生 WXML/WXSS、TypeScript/JavaScript 页面和 CloudBase 云函数。当前主要缺陷来自身份、数据闭环、代码双源、AI 密钥与医学安全，而不是前端框架能力不足。

候选方案：

1. 保留原生小程序 + CloudBase 云函数/数据库，渐进完善；
2. 迁移 Taro/uni-app，继续使用 CloudBase；
3. 重写为 Web/H5 + 独立传统后端；
4. 直接建设微服务和关系型数据库。

## 决策

选择方案 1：

- 原生小程序保留，统一为 TypeScript 唯一源码；
- MVP 使用模块化 CloudBase 云函数和文档数据库；
- 所有核心写操作、身份和 AI 访问迁到服务端；
- 通过契约、repository 和 AI Gateway 保留未来迁移点；
- 达到明确触发条件后，再升级云托管和 MySQL/TDSQL。

## 理由

- 最大化复用已有 UI 和微信生态集成；
- 12 周内可把资源投入在安全与业务闭环，而非框架迁移；
- 当前团队和流量未知，微服务与跨端框架没有证据支持；
- CloudBase 云函数、数据库、存储和认证能力能够覆盖 MVP；
- 通过清晰边界，未来仍可接 Web 管理端或迁移后端。

## 后果

正面：交付快、改动范围可控、运维门槛低。

负面：原生小程序代码不能直接复用到其他端；文档数据库对复杂统计和强关系不如 SQL。使用设计良好的 API 契约、领域 ID 和数据访问层降低锁定成本。

## 重新评估触发条件

- 已批准在 6 个月内发布两个以上非微信端；
- 核心统计查询在文档库上难以满足 SLO 或维护成本明显升高；
- 需要标准 HTTP/OpenAPI、长连接、任务队列或复杂事务；
- 月活、并发、模型成本或团队规模达到现有架构的观测阈值；
- 合规/采购要求指定独立部署或关系型数据库。

重新评估必须有压测、成本、交付期限和团队能力数据，不以“更先进”为理由。
